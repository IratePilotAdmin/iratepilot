## Recommended rollout sequence

1. **Verify target identity.** In Supabase, confirm the exact project ref, branch, and non-production status. Stop if `main PRODUCTION` is a production branch or if its purpose is unclear.
2. **Capture a schema-only baseline.** Use supported Supabase tooling to capture the current remote schema and migration ledger without exporting guest or booking rows. Compare the dump against the repository’s expected base schema and document any drift.
3. **Choose a clean migration lineage.** Prefer the empty `iratepilot-pms-restore-drill-20260925` project for a clean full-history replay of the canonical 148 migrations; local ordered replay passed. Confirm its isolated rehearsal purpose and approved billing first. If using a different rehearsal DB that already has the app schema, establish a dedicated migration track from its verified schema snapshot. Do not use project `trwuofvnqxdpmjztrnwp` or apply a synthetic baseline to it.
4. **Prove the baseline.** Replay the proposed baseline and the ordered 21 feature migrations against an isolated restore/clone. Include migration `202609270159` only after its separate property-state review. Reject any plan that needs unrelated flight, commerce, or account migrations.
5. **Review the exact change set.** Generate a CLI migration list and dry run for the selected target. For this app-wide empty rehearsal baseline, require the list to match the 148-entry checksummed manifest exactly; abort on unknown versions or schema drift. A later PMS-only production rollout needs a separately reviewed migration bundle.
6. **Protect the rehearsal.** Confirm a recent recoverable backup and a tested restore before applying anything to the selected non-production target.
7. **Apply and verify only after the above gates pass.** This rehearsal has completed the schema replay. Re-run read-only checks for migration ledger, tables, RLS, grants, RPCs, triggers, constraints, and disabled-by-default activation controls. Then exercise one authorized sandbox ARI update and reservation round trip with the Red Roof test property.
8. **Keep external distribution disabled** until Booking.com grants the required test account/property access, mappings and financial behavior are reviewed, scheduled workers are deployed safely, and the end-to-end sandbox acknowledgement passes. Expedia remains a separate unimplemented adapter.

## Stop conditions

- Project identity, branch, or non-production status is not verified.
- A baseline would require marking feature migrations applied while their objects are absent.
- A dry run differs from the approved app-wide baseline or cannot match the selected isolated migration track.
- A usable backup/restore path is unavailable.
- The test account, mappings, payments/charges, or reservation acknowledgement cannot be reconciled safely.
