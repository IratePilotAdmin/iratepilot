# Hotel channel adapters

## Booking.com: development-only ARI preparation and test transport

`booking-com/ari.ts` converts explicit room-availability and nightly-rate deltas into Booking.com OTA 2003B XML requests. It groups each request by one mapped Booking.com property, update type, and calendar month; rejects duplicate or out-of-range updates; preserves the selected tax basis; and makes no network calls. `booking-com/inventory-to-ari.ts` converts one property's local inventory snapshots and provider room/rate mappings into delta requests, deduplicates capacity across rate plans, rejects cross-property data and provider-limit violations, and sends nothing. `booking-com/sync.ts` and `POST /api/partner/integrations/booking-com/sync` now load an authenticated owner's saved inventory, build the mapped ARI plan for a maximum 90-day window, hash and idempotently enqueue each request. The partner UI includes a queue action. Database RPC approval gates must pass before enqueue succeeds.

`booking-com/client.ts` provides a guarded test transport. It accepts only explicitly approved test-property scope and the exact provider endpoints, rejects redirects, bounds response size, and parses basic success/error/warning acknowledgements. `lib/booking-com-ari-delivery.ts` connects the approved test token vault, service-role leased outbox, and this transport. `GET /api/cron/booking-com-ari` is bearer-protected and disabled unless `IRP_BOOKING_COM_ARI_SYNC_ENABLED=true`; no Vercel schedule is configured. Tests use fake responses only and never contact Booking.com.

`booking-com/auth.ts` implements a bounded token-exchange helper for Booking.com's current machine-account API-token credentials. It posts only to the official token exchange endpoint, blocks redirects, times out, limits the response size, returns a fixed short cache lifetime, and maps failures to non-sensitive error codes. `booking-com/machine-account.ts` uses the test-only encrypted vault and shared token-exchange ledger before returning a cached or freshly exchanged token. The test ARI worker and `lib/booking-com-reservation-poller.ts` use this runtime; tests inject fake responses and do not contact Booking.com.

`booking-com/credentials.ts` provides a server-only AES-256-GCM envelope for machine-account credentials and an optional cached JWT. Associated data binds each envelope to one test vault ID and environment. Version 1 remains readable through the legacy `BOOKING_COM_CREDENTIAL_ENCRYPTION_KEY` or explicit V1 key; new envelopes use the configured active version (1 or 2), and `reencryptBookingComCredentials` re-encrypts one envelope without returning plaintext to its caller. Migration `202609250153_iratepilot_booking_com_credential_rotation.sql` adds a bounded service-role claim/commit/release workflow with per-account leases, skips accounts undergoing token refresh, and uses full-envelope compare-and-swap before persisting ciphertext under the active key. Its bearer-protected route is disabled unless `IRP_BOOKING_COM_CREDENTIAL_ROTATION_ENABLED=true` and processes at most 10 accounts per call. Keep the V1 key until every V1 vault row and retained recovery copy has been rotated and independently verified; old-key removal verification remains a launch gate. The vault never falls back to PMS or guest-PII keys. Migration `202609250147_iratepilot_booking_com_machine_account_vault.sql` adds a server-only, test-only database vault that stores only these encrypted envelope fields, disabled and unapproved by default. It binds accounts to Booking.com test connections and serializes token-exchange reservations per account, enforcing Booking.com's 30-exchanges-per-hour limit across application instances. Forward migration `202609250152_iratepilot_booking_com_token_refresh_lease.sql` adds an account-row-locked 30-second refresh lease; a competing worker now stops before contacting Booking.com, while expired leases can be reclaimed and failed exchanges release their lease. `booking-com/machine-account.ts` checks the account and approved property connection, reuses encrypted unexpired tokens, rechecks the cache after acquiring the lease, and atomically saves a new encrypted token while clearing its lease. `POST /api/partner/integrations/booking-com` verifies partner property ownership, encrypts submitted **test** credentials before saving, and creates a disabled, unapproved connection; `GET` shows connection metadata only. `GET/PUT /api/partner/integrations/booking-com/mappings` lets the approved property owner read owned-property rooms and save exact provider room/rate-plan IDs against one active local room; every write checks property, room, provider, and environment scope. The partner integrations page includes the test account and mapping forms. The migrations are not applied to production, and no approved provider account is in the vault.

`booking-com/reservations.ts` describes the provider's new-reservation and modified/cancelled queue polls, plus per-message success/failure acknowledgements. `lib/booking-com-reservation-poller.ts` now polls both queues for enabled, approved **test** connections and stages provider-matched messages through the encrypted inbox. The bearer-protected `GET /api/cron/booking-com-reservations` is disabled unless `IRP_BOOKING_COM_RESERVATION_POLL_ENABLED=true`; no recurring schedule is configured. Migration `202609250150_iratepilot_booking_com_reservation_inbox_lifecycle.sql` adds a service-role-only lease, bounded retries, and a durable review state for inbox processing. The worker deliberately sends no acknowledgement because staging is not a durable PMS reservation transaction. The test client requires test-only property scope, reservation access and PII-compliance gates. A success acknowledgement cannot be constructed until the caller confirms durable persistence; when Booking.com's optional response-token feature supplies both the reservation ID and changed-message token, the success acknowledgement preserves both IDs and their source/type attributes, while an error acknowledgement identifies the base reservation. A type-18 response token is rejected unless the base reservation ID is also present. This follows Booking.com's [modified-reservation retrieval](https://developers.booking.com/connectivity/docs/reservations-api/retrieving-modifcancel-reservations-ota) and [acknowledgement](https://developers.booking.com/connectivity/docs/reservations-api/acknowledging-new-reservations-ota) contracts. Reservation response bodies are capped and are not logged or retained by the transport.

`booking-com/reservation-parser.ts` validates bounded OTA XML and normalizes provider IDs, stable room indexes, room/rate mapping IDs, stay dates, guest counts, and the lead guest's basic name/contact fields. For each room stay it preserves whether the provider's total is before or after tax, so downstream accounting does not silently treat an untaxed amount as tax-inclusive. This follows Booking.com's [room-stay](https://developers.booking.com/connectivity/docs/api-reference/roomstay) and [total price](https://developers.booking.com/connectivity/docs/api-reference/total) fields. It ignores unrelated XML fields, including payment-card fields, in its returned value. The parser does not persist the normalized guest data; an atomic PMS reservation/folio transaction is still required before a success acknowledgement may be sent. The database inbox also has a forward-only provider guard so non-Booking.com test connections cannot be staged through the shared inbox RPC.

`booking-com/inbox.ts` encrypts the normalized reservation with AES-256-GCM and property/connection/event-bound associated data, hashes the base reservation ID (not a response token) for replay detection, then submits only the ciphertext and hashes to the service-only inbox RPC. Decryption recognizes the persisted `new`, `modified`, and `cancelled` event values and retains all response-token IDs for the acknowledgement step. It fails closed unless `OTA_RESERVATION_PII_ENCRYPTION_KEY` is configured as a base64-encoded 32-byte key. The accompanying migration installs disabled test-only channel metadata, room mappings, encrypted inbox storage, duplicate detection, and server-only staging. A staged `received` record is not a PMS booking and cannot yet be acknowledged as processed.

Migration `202609250154_iratepilot_booking_com_reservation_pii_retention.sql` adds a service-role-only purge function that clears ciphertext, IV, and authentication tag 30 days after an item reaches `imported`, while keeping status, hashes, and a purge timestamp. Unresolved `review` items are not purged. The bearer-protected `GET /api/cron/booking-com-reservation-retention` processes at most 50 rows per run and is scheduled daily at 05:20 UTC in `vercel.json`; it remains disabled unless `IRP_BOOKING_COM_RESERVATION_RETENTION_ENABLED=true`. The 30-day interval is a conservative connector-inbox default, not a replacement for jurisdiction- and property-specific retention policy approval.

The paired PMS repository now has forward-only migrations `20260925140000_iratepilot_pms_channel_reservation_sources.sql` and `20260925150000_iratepilot_pms_channel_financial_workflows.sql`. They accept a fixed set of channel sources (Booking.com, Expedia, Agoda, Airbnb, Google Hotel, and iRatePilot) in reservation intake, payment review, and balance reporting while preserving existing capacity and maintenance checks. The gateway hashes and namespaces external event and reservation IDs before storing them in the PMS. Local PGlite regressions cover Booking.com create, duplicate, modify, cancel, and unsupported-source rejection, plus source validation across payment and balance workflows. The OTA inbox now assigns a stable per-reservation source version, preserves it on retry, and prevents later messages from passing an earlier message awaiting import or review. A gated worker now bridges cancellation events to the PMS gateway and acknowledges only a matching durable `cancellation-staged`, `duplicate`, or `stale` receipt. A cancellation with no known PMS reservation is retained for review without creating a phantom cancelled stay, and a `review-required` receipt is not acknowledged. New and modified reservations remain in review pending correct financial/folio mapping. The worker route is bearer-protected, disabled unless `IRP_BOOKING_COM_PMS_IMPORT_ENABLED=true`, and has no schedule. The migrations are not hosted or deployed, so external bookings remain unavailable.

This external-provider inbox is separate from the native iRatePilot.com reservation outbox described in `docs/IRATEPILOT-NATIVE-PMS-CONNECTOR.md`. Do not reuse `PMS_CREDENTIAL_ENCRYPTION_KEY` for guest PII. Configure the dedicated key only in the isolated test secret store after approving the target; never commit key material or add it to browser-visible variables.

The local source now implements a guarded subset of the Booking.com reservation lifecycle: single-room and atomic multi-room create/modify imports for complete USD `pay_at_property` folios with supported inclusive tax/fee codes, plus cancellation handling. It requires a matching durable PMS receipt before provider acknowledgement. Unsupported payment models, currencies, charge lines, and multi-room changes/cancellations stay in review. Local tests do not establish a hosted or provider-certified connector. Remaining work includes verifying credential-rotation inventory and recovery copies before retiring the V1 key; confirming property-specific tax/currency and retention configuration; scheduling polling and PII retention; operator review and delivery-status tooling; partner approval, provider certification, hosted migration/deployment, and a partner-authorized sandbox round trip. Production `/api/ota/capabilities` and `/api/pms/ari` currently return 404, and the protected preview cannot be validated without an authenticated session. The public capability route must not report an external OTA as connected or production-ready until those gates pass.

Booking.com requires a Connectivity Partner relationship and property-granted connection scopes before a provider can manage a property's data. Rates/availability and reservations are separate connection types. Current authentication uses property-scoped machine accounts and short-lived bearer tokens; endpoint permissions and any required certification must also be in place. New reservations use `GET` then `POST OTA_HotelResNotif`; changed/cancelled reservations use the corresponding `OTA_HotelResModifyNotif` flow. Reservations require PII compliance approval. See the [Connectivity API overview](https://developers.booking.com/connectivity/docs), [authentication](https://developers.booking.com/connectivity/docs/authentication), [token authentication](https://developers.booking.com/connectivity/docs/token-based-authentication), [endpoint access requirements](https://developers.booking.com/connectivity/docs/managing-endpoint-access), [reservation processing overview](https://developers.booking.com/connectivity/docs/reservations-api/reservations-overview), and [acknowledgement contract](https://developers.booking.com/connectivity/docs/reservations-api/acknowledging-new-reservations). The builders follow Booking.com's [availability](https://developers.booking.com/connectivity/docs/ota-hotelavailnotif) and [rate](https://developers.booking.com/connectivity/docs/ota-rateamountnotif) delta request contracts, but these fixtures are not provider certification.

## Expedia Group

No Expedia Group property-connectivity adapter is implemented. The supported lodging supply surface is a coordinated suite: Availability & Rates, Reservation Management, and Product Management. Expedia's older Booking Notification API is explicitly unavailable for new partner adoption (exceptions require Expedia review); implementation planning should target its newer Reservation Management capability after Expedia confirms eligibility. Product Management is currently pilot-only. Expedia requires partner onboarding, license and PCI review, technical consultation, integration tests, and site review before production. The traveler-facing Rapid API is a separate product, not a substitute for lodging supply connectivity. See Expedia's [Connectivity Hub onboarding](https://developers.expediagroup.com/supply/lodging), [Reservation Management overview](https://developers.expediagroup.com/supply/lodging/docs/booking_apis/reservations/getting_started/ui_guidelines/), [Booking Notification adoption note](https://developers.expediagroup.com/supply/lodging/docs/booking_apis/booking_notification/getting_started/introduction/), and [Product Management availability](https://developers.expediagroup.com/supply/lodging/docs/property_mgmt_apis/product_mgmt/getting_started/intro/).


The current test reservation poller requests Booking.com's `payment_clarity_package_v2` feature. The parser now preserves guest/hotel totals, per-view tax lines, and withheld-tax lines in the encrypted inbox. Booking.com's latest guidance distinguishes the amount collected from the guest (GuestView) from the property's disbursement/collection perspective (HotelView); these values and tax type semantics depend on the property's payment and business model. Reconciliation against PMS tax configuration and atomic reservation/folio import are still missing, so staged messages must not be treated as posted PMS folios. See the official [Payments Clarity Package v2 guide](https://developers.booking.com/connectivity/docs/reservations-api/implementing-payments-clarity-package-v2-ota).
